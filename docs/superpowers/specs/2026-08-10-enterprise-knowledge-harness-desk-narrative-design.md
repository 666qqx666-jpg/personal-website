# Enterprise Knowledge Harness Desk 叙事重构设计

## 1. 设计摘要

本设计重构个人网站 `/ai/knowledge-harness/` 的展示内容。页面继续使用现有单页沉浸滚动与左右分栏 Deck，但主叙事从“企业知识平台模块清单”转为一条面向招聘者、管理者和业务负责人的产品判断链：

1. 企业知识为什么不能只靠文档入口或检索。
2. 对话与材料怎样先形成候选，再经过门禁成为正式知识。
3. V1 怎样建立首个稳定基线。
4. 为什么提出并实现 V2 影子实验。
5. 为什么人工评测后没有直接切换 V2。
6. 如何收敛为 Profile 驱动、两阶段组装的 V1.5。
7. 这套系统如何进入真实产品工作流。

采用已确认的组合：

- **A 为骨架：能力叙事型。** 访客先看见问题、判断、决策与结果。
- **C 为证据：版本演进型。** V1 → V2 实验 → 评测回流 → V1.5 收敛，为产品判断提供技术证据。

页面最终应让访客形成以下心智：

> 这不是一个追求召回更多的 RAG 项目，而是一套从知识候选、人工裁决、任务加载到版本评测都可治理的企业知识产品。

## 2. 目标、受众与成功标准

### 2.1 主要受众

- 招聘者。
- 管理者与业务负责人。
- 次要受众为希望继续了解实现细节的技术访客。

### 2.2 页面任务

访客在 3–5 分钟内应能回答：

- 这个系统解决的企业问题是什么。
- 知识卡什么时候产生，为什么不是每次对话都自动生成。
- V1、V2、V1.5 分别解决了什么问题。
- 为什么技术更复杂的 V2 没有直接替换 V1。
- V1.5 怎样继承 V1 的有效性并吸收 V2 的经验。
- 系统是否进入了真实工作流，而不只是架构 Demo。

### 2.3 成功标准

- 一级文案以业务问题、产品判断和结果为主，不要求访客先理解 Query Planner、RRF 等组件。
- 右侧结构图保留足够技术深度，能支撑 V1/V2/V1.5 的真实性。
- 所有版本状态、预算、评测数字和业务结果均可回到本地真值源。
- 左侧叙事和右侧图形承担不同职责，不复制同一段文案。
- 桌面、移动端、明暗主题和时间线导航继续可用。

## 3. 原型路由判断

- **模式：** 既有系统增量。
- **是否快速通道：** 否。信息架构和状态表达发生产品级变化，已通过低保真方案比较和逐段确认收敛。
- **baseline-evidence：** PASS。
- **high-fidelity-readiness：** 本 Spec 经用户复核后可转为 PASS。
- **当前可进入阶段：** 正式设计 Spec 与实施计划准备。
- **尚未进入：** 正式页面实现。

## 5. 已确认的产品决策

1. 页面主要服务招聘者、管理者和业务负责人，技术访客为次要受众。
2. 采用“能力叙事型”为主骨架，“版本演进型”为证据层。
3. 版本主线不是 V1 → V1.5 → V2，而是：

   ```text
   V1 稳定基线
   → 发现规模与复杂度问题
   → V2 Shadow 实验
   → 人工评测发现工作价值不如 V1
   → 收敛为 V1.5
   ```

4. V1.5 不是 V2 失败后的简单回退，而是：
   - 保留 V1 在小语料与人工权威索引上的有效性。
   - 吸收 V2 的 Profile 驱动、查找与审查组装职责分离、RetrievalTrace / 可观察性、可替换检索接口。
   - 为未来平滑切换 V2 保留稳定接口与运行边界。
   - 当前作为评测后的收敛决策与过渡架构呈现；在没有独立运行证据前，不宣称 V1.5 已完成生产切流或全面验证。
5. 知识产生采用双门：
   - 第一门为任务内语义触发的即时候选捕获。
   - 第二门为正式入库裁决。
6. 即时候选捕获不是每个对话都触发，也不是会话结束 Hook 自动拆卡。
7. 候选阶段不要求当场证明一定会成为正式经验；只要求可能改变未来跨任务行为，并有用户原话或可定位材料。
8. V1 最多返回 5 个文件，没有 Token 硬上限。
9. V2 Context-Pack 硬上限为 6,000 Token，不是 6,500。
10. V1.5 继续保留 6,000 Token 安全硬上限；3,500 不作为硬门。
11. V1.5 预算下调必须基于 V1/V1.5/V2 同题评测：工作价值不降低，且 V1.5 的 Token 中位数、P90 均低于 V2；取得真实分布后再决定新上限。
12. 当前可公开盲评证据为 20 组任务、V1 工作价值 18、V2 工作价值 16；不能从该报告推出 V1.5 的 Token 结论。

## 7. 四幕八章信息架构

### ACT I · WHY：建立问题与价值

#### 01 · 封面

- **标题：** Enterprise Knowledge Harness。
- **核心句：** 让企业经验成为 Agent 可复用的判断力。
- **副标题：** 让多个 Agent 与产品经理基于同一事实工作。
- **信号行：** 知识产生 · 按任务交付 · 评测演进 · 工作流结果。
- **右侧 / 背景视觉：** 知识产生 → 交付 → 演进 → 结果的四步价值链，不展开组件名。
- **保留：** 负责人、时间、企业复用状态与滚动提示。

#### 02 · 企业问题

- **标题：** 知识存在，不等于 Agent 能正确使用。
- **左侧叙事：**
  - 问题：规范、项目经验和业务材料分散，来源权威不一致。
  - 后果：全量加载造成膨胀；冲突和过期材料会静默进入回答；规则写死在 Skill 中导致知识和流程耦合。
  - 判断：企业知识平台首先治理“什么能进入任务、由谁裁决、如何失败”，再谈检索能力。
- **右侧视觉：** 复用并调整 `ProblemMap`。主要业务后果为上下文膨胀、来源冲突、材料过期、加载成本；`Skill` 耦合降为技术注释。

### ACT II · OPERATE：候选生产与首个稳定系统

#### 03 · 知识产生

- **标题：** 先捕获候选，再决定什么值得成为知识。
- **主判断：** 即时候选捕获与正式知识生产是两个不同门槛。
- **三类触发入口：**
  1. 任务内即时捕获：可能改变未来跨任务行为，且有用户原话或可定位证据。
  2. 用户显式沉淀：用户要求 digest、保存对话或导出知识。
  3. 复现与周度复盘：同类证据再次出现，或周度复盘恢复候选。
- **排除：** 纯 Agent 推断、当前 TODO、项目进度、一次性 Bug 和仅对当前任务有效的决定。
- **候选流：**

  ```text
  识别复用信号
  → 写入候选队列并去重 / 追加证据
  → 显式沉淀、复现或周度复盘触发复审
  → 入库五问
  → 新增 / 追加 / 合并 / 暂缓 / 丢弃 / 留原文层
  ```

- **入库五问：** 会复用吗、会改变判断吗、能被路由吗、已有卡能承接吗、会污染上下文吗。
- **三层去向：** 原文层、正式知识域、能力层 / shared Skill。
- **实现注释：** 即时候选由 Agent 行为规则做语义判断，再由确定性队列脚本持久化；不是宿主 Hook。`digest` 为用户显式触发的完整沉淀流程。
- **右侧视觉：** 新建双门知识生产图；合并旧 `KnowledgePipeline` 与 `LayeredArchitecture` 的有效语义。

#### 04 · V1 起点

- **标题：** V1：用人工索引建立第一个稳定基线。
- **主判断：** 小语料阶段，人工权威索引能以低复杂度稳定完成任务路由。
- **运行路径：**

  ```text
  Task
  → 根 / 领域索引
  → 任务索引
  → 项目记忆索引
  → 最多 5 个文件
  → Context-Pack
  ```

- **预算事实：** V1 限制最多返回 5 个文件，没有 Token 硬上限。
- **演进问题：** 文件长度不一导致上下文波动；知识、角色和跨项目材料增加后，人工维护与覆盖成本上升。
- **右侧视觉：** 新建 V1 单泳道运行图，合并 `RoutingIndexMap` 与 `ContextAssembly` 的 V1 路径。

### ACT III · LEARN：V2 假设、评测与 V1.5 收敛

#### 05 · V2 Shadow

- **标题：** V2：为规模化问题设计影子实验。
- **主判断：** V2 用更强的检索、排序和可观察性验证未来规模化假设，不直接接管生产流量。
- **查找职责：** Query Planner、RoleRetriever、Exact / Lexical / Metadata、角色内 RRF、Role-aware Reranker。
- **审查组装职责：** 去重、冲突分组、Selector、Quality Gate、Composer、Renderer。
- **输出：** RetrievalTrace，记录候选、排序、门禁和选择结果。
- **预算：** Context-Pack 最终字符串硬上限 6,000 Token。
- **五区预算：**

  | 区域 | 上限 |
  | --- | ---: |
  | Envelope、选择原因、冲突和缺口 | 300 |
  | Current Task 摘要 | 1,400 |
  | Control | 800 |
  | Formal + Legacy | 2,600 |
  | Evidence | 900 |
  | **合计** | **6,000** |

- **右侧视觉：** 合并 `RankingMechanism` 与 `ContextAssembly` 的 V2 路径；五区预算作为图中技术证据，不进入左侧主文案。

#### 06 · 人工评测与版本决策

- **标题：** 更少上下文，没有带来更高工作价值。
- **已验证证据：**
  - 20 组同题盲评。
  - V1 工作价值 18。
  - V2 工作价值 16。
  - 安全门与规模门通过。
  - 激活门为 false，生产未启用。
- **产品判断：** 技术门通过不等于工作价值门通过；更完整的工程能力和更少上下文不能自动成为切流理由。
- **状态：** V2 保持 Shadow，不进入 canary；保留原子切换与回滚能力。
- **证据边界：** 该评测比较 V1 与 V2，不证明 V1.5 的 Token 分布或工作价值。
- **右侧视觉：** 重构 `ReleaseRollback` 为“评测结果 → 激活门 → canary / 不切换”的决策图；18 / 16 为主视觉，版本泳道为次级证据。

#### 07 · V1.5 当前收敛设计

- **标题：** V1.5：把有效性与可扩展性收敛在一起。
- **主判断：** V1.5 不回到原 V1，也不直接切换 V2；它先改变知识选择与组装方式。
- **运行路径：**

  ```text
  Task
  → Profile 判断任务、角色与知识边界
  → 第一阶段：查找候选
  → 第二阶段：审查、冲突处理与组装
  → Context-Pack
  ```

- **从 V1 保留：** 人工权威索引、小语料有效性、显式未加载与风险。
- **从 V2 吸收：**
  - Profile 驱动。
  - 查找与审查组装职责分离。
  - RetrievalTrace / 可观察性。
  - 可替换检索接口，为未来平滑切换 V2 留出边界。
- **质量行为：** 弱相关不加载；冲突保留冲突组；过期标记复核；关键缺失输出 insufficient / escalation；高风险事实交给人工确认。
- **预算：**
  - 保留 6,000 Token 安全硬上限。
  - 3,500 不作为硬门，不在公开页面表现为已验证阈值。
- **预算下调门：**
  1. 使用同一问题集比较 V1、V1.5、V2。
  2. V1.5 工作价值不得降低。
  3. V1.5 Token 中位数低于 V2。
  4. V1.5 Token P90 低于 V2。
  5. 取得真实分布后，再决定是否降低硬上限。
- **右侧视觉：** 新建 Profile 两阶段架构图；吸收旧 `FailureBoundary` 的异常行为，并把评测门显示在预算下调出口。

### ACT IV · IMPACT：真实产品结果

#### 08 · 真实结果

- **标题：** 从知识治理进入真实产品交付。
- **接入：** PRD Writer 与独立 Reviewer 使用同一知识事实基线。
- **覆盖：** 产品部门全员覆盖，渗透率 100%；保留“历史文档缺失的产品优化需求除外”的事实边界。
- **复用结果：** 规则、案例和项目记忆能独立维护、按任务加载并版本化演进。
- **收尾判断：** 系统价值来自更稳定的工作交付与跨工作流复用，不来自把 V2 技术指标包装成业务成果。
- **右侧视觉：** 复用并调整 `WorkflowImpact`。

### 13.1 信息职责

- 左侧：问题、判断、决策、状态和结果。

### 13.2 渐进技术深度

- 不新增必须点击才能理解主故事的弹窗或抽屉。

### 13.3 章节密度

- 每章只允许一个主判断。
- 左侧 Narrative 建议 3–4 行，每行由短标签和 1–2 句正文组成。
- 右侧图优先展示 4–7 个主节点；更细组件使用分组、次级标签或 Caption。
- 评测章节的 18 / 16 是主视觉，6,000 五区预算是技术证据，不与主数字争夺层级。

- S5、S6、S7 为移动端高密度章节，需要独立快照。

### 13.5 可访问性

- 每个 Figure 保留可描述关系的 `aria-label`，不能只罗列节点名。

- Hash 导航、主题切换和键盘 Focus 状态继续可用。
