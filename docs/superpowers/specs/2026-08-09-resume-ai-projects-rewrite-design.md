## 1. 目标

## 4. 项目一：企业产品交付 Agent Harness

### 4.1 定位

- 名称：企业产品交付 Agent Harness。
- 角色：产品设计与架构负责人。
- 时间：2026.04–至今。
- 状态：内部复用｜持续完善工作包。

### 4.2 项目背景

早期 PRD、报价和原型能力分别沉淀在独立 Skill 中，模板、规则和经验直接写在 Skill 正文里。随着迭代增加，Skill 不断膨胀，企业知识难以维护；PRD 写作与审查处于同一对话时，又会继承相同假设和上下文缓存，容易遗漏问题。涉及历史项目时，还需要反复查找旧代码、文档和项目决策。

### 4.3 产品判断

企业 Agent 不应把全部知识写死在 Skill 中，而应将稳定工作流与企业知识分离：Skill 负责流程、角色和质量门禁，企业知识库负责按任务加载规则、经验和项目记忆。

### 4.4 关键行动

- 重构 PRD Skill，将企业模板、业务规则与历史经验迁移到企业知识库，按照需求发现、PRD 写作和独立审查等任务类型组装最小上下文。
- 将 PRD 生产拆分为 Writer 与冷启动 Reviewer 两个隔离工作流，避免审查阶段继承写作对话中的假设；存在关键问题时阻止文档进入后续交付。
- 增加项目依赖门控：涉及存量系统时，先识别历史代码、文档和项目决策依赖，再从企业知识库的项目记忆模块按需加载。
- 建设原型工作流，基于已经封口的 PRD 和真实页面基线生成高保真原型，并建立原型结束后的 PRD 同步门，减少产品、UI 与前端之间的理解偏差。
- 建设报价工作流，根据需求蓝图、功能边界和交付范围生成结构化报价单，减少产品经理、项目经理和销售的人工拆分与反复核对。

### 4.5 结果证据

- 企业知识库与 PRD 写作、独立审查工作流已由多名公司同事使用。
- 在真实产品任务中，将 PRD 从写作到通过独立审查、达到可交付状态的周期，由近 1 个月缩短至约 2 周。
- 将 PRD、原型与报价能力封装为可复用工作包，连接需求澄清、方案设计、质量审查和商务交付。

### 4.6 关键词

企业 Agent / PRD Writer / 独立 Review / 项目依赖门控 / 原型与报价工作流

## 5. 项目二：Enterprise Knowledge Harness

### 5.1 定位

- 名称：Enterprise Knowledge Harness｜企业知识与上下文平台。
- 角色：产品设计与架构负责人。
- 时间：2026.04–至今。
- 状态：企业复用｜持续演进。

### 5.2 项目背景

企业规范、历史项目经验和业务文档分散在不同系统中。直接把全部材料塞入模型会导致上下文膨胀、来源冲突和加载成本增加；把规则长期写在 Skill 中，又会使工作流与企业知识相互耦合，难以独立升级。

### 5.3 产品判断

企业知识库不能只是文档集合，而应同时解决知识生产、权威治理、最小上下文组装、版本发布和失败回滚，使多个 Agent 和多个产品经理基于同一事实工作。

### 5.4 整体架构

- 企业原始文档继续作为动态事实真值源。
- 知识系统拆分为原始材料、正式知识、企业能力包和 Agent 工作流。
- 通用 Skill 负责流程与质量门禁；企业能力包负责术语、规范、案例索引、项目记忆和知识契约。
- 通过版本化发布，将企业知识与对应 Skill 组合为兼容、可追溯的稳定运行版本。

### 5.5 知识生产与迁移

- 建立“材料快照—内容切分—证据片段—候选知识卡—人工裁决—正式知识”的生产链路。
- 为候选知识附带来源、适用范围、版本和证据，未经确认的经验不直接成为企业规则。
- 参考 AI 产品经理训练营的迁移实践，对历史企业文档进行分批加工和增量迁移，避免一次性搬迁造成重复内容与知识污染。

### 5.6 上下文治理

- 使用压缩 Skill 控制工作流自身的加载体积，将具体规则和经验迁出 Skill。
- 建立领域索引、任务索引和项目记忆索引，根据任务类型、项目范围和知识权威顺序按需加载。
- 引入知识卡组装与排序机制，综合相关性、权威性、时效性和上下文预算生成最小充分上下文。
- 对弱相关、冲突、过期和缺失材料定义降级或人工确认行为，避免模型静默补全企业事实。

### 5.7 安全演进

- 使用 canary、stable、版本校验和兼容关系管理知识包与 Skill。
- 采用原子切换和生产级回滚机制，新版本异常时继续使用上一稳定组合。
- 在不影响现有 V1 使用的前提下逐步引入 V2 的索引、组装和排序能力。

### 5.8 结果证据

- 企业知识库已与 PRD Writer、独立 Reviewer 工作流连接，并由多名公司同事用于真实产品任务。
- 将企业知识从固定 Skill 正文中解耦，使规则、案例和项目记忆能够独立维护、按需加载和版本化演进。

### 5.9 关键词

企业知识库 / Context Engineering / 知识候选治理 / RAG / 版本发布与回滚

## 6. 项目三：全渠道销售线索管理系统

### 6.1 定位与贡献边界

- 名称：全渠道销售线索管理系统。
- 角色：产品线负责人。
- 时间：2025.04–至今。
- 状态：核心链路已上线｜持续商业化演进。
- 七个平台接入及整套销售线索系统均由本人从 0 到 1 负责。
- 旧材料中“早期多平台接入底座由前任产品负责人建设”的记录错误，不再用于完整版简历。

### 6.2 项目背景

连锁品牌的销售线索分散在多个内容、交易和本地生活平台，依赖人工下载、导入和分配；大量平台门店尚未被品牌认领，线索无法及时匹配到具备服务能力的门店，也缺少跟进、回收和再次分发机制。

### 6.3 本人职责

从 0 到 1 负责整体销售线索系统的产品建设，主导抖音、快手、美团、小红书、高德、微信和支付宝七个平台接入，以及采集整合、任务生命周期、智能分发、公海池、自动回收和后续商业化演进。

### 6.4 关键行动

- 统一七个平台的线索来源、门店和状态口径，将采集数据接入销售线索任务生命周期。
- 针对大量平台门店尚未认领、线索需要分配给就近或成交能力更强门店的问题，设计候选门店筛选和智能分发机制。
- 通过资格过滤、保护期、分阶段扩圈、公海池认领与超时回收，形成可解释、可配置、可回收的责任闭环。
- 识别“门店自驱力不足无法只靠分发规则解决”，进一步将线索体系设计为品牌治理下的门店采购模式，并将付费认领兼容进既有智能分发、任务和回收生命周期，避免重新建设一套孤立购买系统。

### 6.5 结果证据

- 覆盖约 10 个付费品牌、约 15,000 家上线门店。
- 平台累计处理约 102.6 万条线索，当前月处理量约 10 万—30 万条。
- 某匿名客户约三个月、月均约 10 万条线索，卡券核销率由不足 49.4% 提升至 61.7%。

### 6.6 关键词

全渠道接入 / 任务生命周期 / 智能分发 / 公海池 / 商业化演进
