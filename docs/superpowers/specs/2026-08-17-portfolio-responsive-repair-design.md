## 2. 问题证据

### 2.1 首页 Desk 卡片在中等宽度下失衡

用户截图对应约 738 CSS px 的中等宽度。首页精选工作在 `960px` 以下会把 Enterprise Product Delivery Agent Harness 卡片移到下一行，但卡片仍沿用桌面竖向辅助卡结构。截图因此被放大为接近整页宽度，卡片高度明显超过其信息价值，看起来像布局意外掉落。

### 2.2 Knowledge Harness 在窄桌面下裁切结构图

用户截图对应约 899 CSS px。页面仍使用左右双栏，右侧证据画布只有约 430px，但内部 V2 架构、报告对照和决策门仍依据整个视口宽度选择桌面布局。子组件的最小内容宽度超过右栏，页面又通过 `overflow-x: hidden` 隐藏溢出，最终出现证据画布和文字被右侧裁切。

### 2.3 现有测试的盲区

当前测试只比较 `document.documentElement.scrollWidth` 与视口宽度。由于页面主动隐藏横向溢出，即使结构图内部已经超出可见区域，这项检查仍可能通过。

## 3. 目标与非目标

### 3.1 目标

1. 中等宽度下，首页 Desk 卡片即使换行也要呈现为有意设计的紧凑证据条，而不是放大的桌面侧卡。
2. Knowledge Harness 在证据画布无法完整容纳时提前切换为“叙事在上、结构图在下”。
3. 结构图根据自身容器宽度适配，不再只依赖浏览器视口宽度。
4. 手机端保持章节、标题、叙事、完整结构图、图例和图注的阅读顺序。
5. 用实际元素边界、内部滚动宽度和关键网格列数建立回归测试。

### 3.2 非目标

- 不改首页和案例正文。
- 不更换截图、配色、字体、卡片视觉语言或章节顺序。
- 不重做 Skill Desk 页面结构。
- 不修改 Knowledge Harness 的事实、验证数字或版本状态。
- 不推送、部署或创建 PR。

## 4. 方案比较

### 方案 A：中等宽度紧凑重排（采用）

- 首页仍按 Knowledge Harness、Desk、业务案例的顺序换行，但 Desk 在平板和窄桌面使用“左文右图”的紧凑横向结构。
- Knowledge Harness 在窄桌面提前改为上下排列；密集图表再依据容器宽度收缩。
- 优点：保留既定信息优先级，桌面不受影响，中等宽度不会产生巨大卡片或证据裁切。
- 代价：需要同时维护桌面、中等宽度和手机三档行为。

### 方案 B：所有中等宽度继续强制双栏（不采用）

- 首页和 Knowledge Harness 都尽量保持桌面双栏，只压缩字号、间距和图表节点。
- 优点：页面纵向长度较短。
- 缺点：中文叙事和证据图会同时失去可读性，容易再次出现“技术上没有滚动条、视觉上已经被裁切”的假通过。

### 方案 C：桌面以下全部单列（不采用）

- 首页和案例在较早断点直接全部纵向排列。
- 优点：实现简单，最不容易溢出。
- 缺点：平板和小型笔记本空间利用率过低，Desk 卡片仍可能因全宽截图变得过高。

## 5. 已选响应式行为

### 5.1 首页精选工作

#### 宽桌面

- 保留现有非对称双栏：Knowledge Harness 为主卡，Desk 为侧卡。
- 业务案例继续占下一行双列。

#### 中等宽度（641–960 CSS px）

- 精选工作按 Knowledge Harness、Desk、业务案例顺序排列。
- Desk 卡片改为紧凑横向结构：文字在左、真实审查截图在右。
- 图片保持 `16:9` 证据窗口并限制高度，避免卡片接近整屏高。
- Knowledge Harness 主卡可继续纵向呈现，但结构图不得产生竖排文字或内部溢出。
- 两个业务案例继续双列；只有手机端再切为单列。

#### 手机（不大于 640 CSS px）

- 四项工作依次单列。
- Desk 恢复文字在上、截图在下，避免横向区域过窄。
- 图片按容器宽度展示，标题和说明自然换行，不缩小到难以阅读。

### 5.2 Enterprise Knowledge Harness

#### 宽桌面

- 保留左侧叙事、右侧结构图的既定版式。

#### 窄桌面与平板（不大于 1080 CSS px）

- 在 `1080px` 及以下提前切换为单列；`1081px` 及以上保留桌面双栏。
- 顺序固定为：章节、标题、叙事、结构图、图例、图注。
- section 允许随内容增长，不再被固定视口高度裁切。
- 结构图容器设置 `min-width: 0`，密集图表依据容器宽度而非整页宽度切换布局。

#### 手机

- 五层架构改为逐层纵向阅读。
- 两份验证报告改为单列。
- 不切流决策链改为纵向流程，箭头方向随布局变化。
- 底部章节导航保留圆点与当前章节状态，隐藏非必要长标签。

### 5.3 Skill Desk 邻接验收

本轮不改 Skill Desk 页面设计，只验证其现有响应式规则没有出现横向溢出、卡片断裂、导航遮挡或不可用链接。若发现与本次改动无关的问题，单独列入结果，不扩大修复范围。

## 8. 自动化验收条件

### 首页

- 宽桌面下 Knowledge Harness 与 Desk 保持双栏。
- 768px 下 Desk 位于 Knowledge Harness 之后，并采用两列紧凑结构。
- 390px 下 Desk 改为单列，业务案例也为单列。
- 所有卡片边界位于视口内，页面不存在横向滚动。

### Knowledge Harness

- 1280px 下核心章节保持双栏。
- 1024px、834px、390px 下核心章节为单列。
- 每张 `.kh-frame` 的 `scrollWidth` 不超过自身 `clientWidth`。
- S5、S6、S7 的结构图、报告和决策节点均落在画布可见边界内。
- section 的实际内容高度不超过其可滚动承载范围，标题、图例和图注均可见。
- 底部章节导航和主题切换继续可用。

### Skill Desk

- 1024px、834px、390px 下无横向溢出。
- 导航、卡片、标签和详情入口仍可见、可点击。

## 9. 视觉验收方式

1. 第一轮同时生成桌面、平板和手机截图，集中判断所有断点问题。
2. 在一个批次内修复截图暴露的问题。
3. 最多再进行一轮确认截图，不进入无限微调。
4. 同时运行类型检查、定向 E2E、无障碍检查和构建。

## 10. 完成定义

只有同时满足以下条件才算完成：

- 用户截图中的 Desk 失衡和 Knowledge Harness 裁切均不可复现。
- 七档视口均无横向溢出或隐藏裁切。
- 手机端图文顺序清楚，结构图不依赖缩小字号维持桌面布局。
- 既有桌面视觉方向、事实与内容保持不变。
- 定向测试、类型检查、构建和响应式视觉复核通过。
