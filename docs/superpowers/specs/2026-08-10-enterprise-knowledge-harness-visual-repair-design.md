# Enterprise Knowledge Harness 视觉与叙事修复设计

## 1. 文档状态

- 日期：2026-08-10
- 当前状态：用户已确认，允许进入实施计划
- 目标页面：`/ai/knowledge-harness/`
- 事实母稿：`docs/resume/完整版-简历.md`
- 动态技术状态补充来源：Knowledge Context V2 正式 Spec、当前主线状态与可复核盲评结果
- 设计结论：采用“选择性复用旧构图 + 统一重绘”的企业版修复方案

## 2. 问题与根因

2026-08-09 的企业版升级把 `enterpriseSections` 中同一个 `points` 数组同时渲染到左侧叙事区和右侧所谓“结构图”。这使左右两栏逐字重复，并将旧版九组不同语义的 SVG 结构图替换为同一种编号卡片。

问题不只是重复文案，还包括：

1. 原页面“一页一个视觉解释”的案例表达能力被删除。
2. 左侧产品叙事和右侧系统解释失去职责分工。
3. 九页不同的企业知识机制被压平成同一种列表。
4. 自动化测试只验证章节、关键词和溢出，没有验证左右语义差异和视觉退化。
5. 页面将“三层索引”整体误写为 V2 逐步引入，混淆了 V1 当前运行索引与 V2 派生检索 Runtime。

## 3. 修复目标

本次修复需要同时完成四件事：

1. 保留 Enterprise Knowledge Harness 的企业版名称、事实、角色、时间、职责和结果证据。
2. 恢复旧版的信息密度、案例故事感与“一页一个独立结构图”的表达质量。
3. 精确区分 V1 当前稳定路径与 V2 已实现但未切流的影子演进路径。
4. 从数据结构、组件边界和自动化测试三层阻止左右重复再次发生。

成功后的页面应让访客在十段 Deck 中理解：

```text
企业知识为什么成为 Agent 的基础问题
→ 为什么知识平台不能只是文档集合
→ 知识如何生产、治理和路由
→ 当前 V1 如何稳定组装 context-pack
→ V2 如何升级检索、排序与质量门禁
→ 为什么 V2 尚未切流
→ 平台如何接入真实 PRD 工作流并产生已验证结果
```

## 4. 非目标

- 不恢复完整的个人学习时间线。
- 不恢复个人工具数量、个人知识卡数量或个人多 Agent 数字。
- 不把已废弃的个人 Claude Writer / Codex Reviewer 流程写成企业方案前身。
- 不回滚 Enterprise Knowledge Harness 名称和企业版事实。
- 不重做全站视觉系统或 `DeckLayout`。
- 不新增 Agent Harness 独立项目页。
- 不修改完整版简历、PDF、About、Skill Desk 或商业项目内容。
- 不在本次修复中启用 Knowledge Context V2、改变 memory-loader 流量或修改真实知识库。
- 不部署、不推送远端、不创建 Pull Request，除非用户另行授权。

## 5. 事实来源与状态契约

### 5.1 来源优先级

公开事实按以下优先级处理：

1. 用户在本轮明确确认的事实和状态纠正。
2. `docs/resume/完整版-简历.md` 中的项目名称、角色、时间、职责、关键行动和结果数据。
3. `/Users/qqx/Documents/Obsidian Vault/能力层/记忆维护/当前主线状态.md` 中的当前 V1/V2 动态状态。
4. `/Users/qqx/my_code_cursor/learn_for_product/docs/superpowers/specs/2026-07-26-knowledge-context-v2-deterministic-retrieval-composer-design.md` 中的 V2 架构。
5. 可复核的离线盲评、影子运行和测试证据。
6. 旧页面只作为交互和视觉资产参考，不作为当前事实来源。

网站可以比两页 PDF 和完整版简历更完整，但不得改变项目身份、责任、状态或结果归属。

### 5.2 已稳定运行

页面可使用稳定运行口径表达：

- 原文层、正式知识域、能力层的三层知识架构。
- 根索引、任务域索引、任务路由和项目记忆索引。
- 企业知识与固定 Skill 正文解耦。
- V1 memory-loader / context-pack 路由、候选筛选和预算裁剪。
- 企业规则、经验与项目记忆按任务加载。
- Enterprise Knowledge Harness 接入 PRD Writer 与独立 Reviewer。
- 产品部门团队覆盖和完整版简历已经确认的结果证据。

### 5.3 已实现但未切流

页面必须明确标为“工程已实现 / 影子验证 / 暂未激活”：

- V2 可重建派生索引与原子快照。
- Query Planner 的任务、约束和查询角色规划。
- RoleRetriever 的 Exact、Lexical、Metadata 三通道召回。
- 按角色 RRF 融合与 Role-aware Reranker。
- 去重、冲突分组、Selector、Quality Gate 和 RetrievalTrace。
- V2 影子运行、安全门和规模增长门。

截至 2026-08-10，V2 最近有结论的工作价值盲评仍低于 V1，当前主线状态明确为“V1 稳定基线，V2 暂不启用”。页面不得用“持续演进”掩盖未激活事实，也不得把技术门通过写成企业业务结果。

### 5.4 关于“两块 Skill”的精确口径

V2 的真实设计是同一 `memory-loader/context_v2` Runtime 内的职责拆分，不是两个已经上线的独立 Skill：

```text
查找职责
Query Planner → RoleRetriever

审查与组装职责
RRF / Reranker → 去重与冲突 → Selector → Quality Gate → Composer / Renderer
```

页面可用“找”与“审查组装”帮助理解职责，但必须明确它们属于一条 Runtime，而不是两个独立 Skill。

## 6. 方案选择

### 6.1 已选方案：选择性复用 + 统一重绘

保留旧版有效的图形构图、左右分栏、滚动 Deck、图注和整体视觉气质；语义已经变化的页面重新设计。九张图共享颜色、节点、线型、字号和状态图例，但保持九种不同拓扑。

选择该方案的原因：

- 能恢复旧版已经验证的视觉表达质量。
- 不需要让旧个人叙事勉强适配企业语义。
- 比全量回滚更准确，比完全重做风险更低。
- 每张图可以独立表达，同时保持整体一致。

### 6.2 未选方案

#### 方案 A：旧版结构直接企业化

优点是恢复快、最接近旧版。缺点是部分旧图围绕个人学习、个人三层演进和个人多 Agent 设计，直接换字会造成新的语义错配。

#### 方案 B：全新统一图形系统

优点是企业感和一致性最强。缺点是九页全部重画，工作量和再次偏离旧版气质的风险最高。

### 7.1 故事视角

主线是企业知识平台产品故事，不恢复完整个人成长时间线。只在能解释产品决策来源时保留演进证据，例如：

- 为什么从 Skill 内嵌知识转向工作流与知识解耦。
- 为什么 V1 仍被保护为稳定基线。
- 为什么 V2 工程完成后仍需价值激活门。

## 8. 页面版式与视觉语言

### 8.1 左侧叙事

左侧恢复语义标签，不使用机械 `01/02/03` 编号。每页根据内容从以下标签中选择 2–4 个：

```text
背景 / 问题 / 影响 / 判断 / 原则 / 决策 / 机制 / 边界 / 当前 / 升级 / 门禁 / 接入 / 覆盖 / 结果
```

规则：

- 不要求每页凑满固定三项。
- 标签说明叙事层次，不替代正文。
- 必要时允许一条短产品判断或引用。
- 网站正文可比简历更完整，但不得增加未经确认的数字或状态。

### 8.2 右侧结构图

每张结构图必须满足：

1. 脱离左侧正文仍能被理解。
2. 节点、连线和图例表达关系，而不是重新排版左侧句子。
3. 使用本页专属的结构拓扑。
4. 包含独立标题、图注和无障碍说明。
5. 图形标签允许与左侧共享必要术语，但不得逐句复述叙事段落。

### 8.3 统一视觉语法

| 视觉语法 | 含义 |
| --- | --- |
| 默认实线节点 | 当前稳定架构或稳定运行能力 |
| 青色强调或青色虚线 | V2 工程已实现、影子验证或逐步引入 |
| 橙色虚线 / 警示节点 | 冲突、缺失、过期、人工门禁或价值激活门 |
| 绿色节点 | 已验证接入和业务结果 |
| 紫色节点 | Composer、决策或跨模块编排 |

不能只依赖颜色区分状态；图例必须同时使用线型和文字。

### 8.4 代表页基线

用户已确认 S6“上下文组装”修正版可以作为统一版式基线：

- 桌面端约 `38–42%` 左侧叙事、`58–62%` 右侧结构图。
- 左侧保持 3 个主要语义块和可选短判断。
- 右侧展示完整图形、状态图例和图注。
- 移动端按“章节 → 标题 → 左侧叙事 → 完整结构图 → 图例与图注”排列。
- 移动端不把结构图节点拆散到叙事块之间。

## 9. 组件与数据边界

### 9.1 核心原则

左侧叙事数据与右侧视觉数据必须从代码结构上分离。

禁止再次出现：

```astro
左侧：points.map(...)
右侧：points.map(...)
```

### 9.2 建议组件结构

```text
src/pages/ai/knowledge-harness.astro
src/data/knowledgeHarness.ts
src/components/knowledge-harness/
  DiagramFrame.astro
  ProblemMap.astro
  LayeredArchitecture.astro
  KnowledgePipeline.astro
  RoutingIndexMap.astro
  ContextAssembly.astro
  RankingMechanism.astro
  FailureBoundary.astro
  ReleaseRollback.astro
  WorkflowImpact.astro
```

职责：

- `knowledgeHarness.ts`：只保存章节信息和左侧叙事块，不保存九张图的完整节点数组。
- `DiagramFrame.astro`：统一图形容器、图例、图注、响应式和无障碍接口，不决定具体拓扑。
- 九个视觉组件：分别拥有本图的节点、连接、状态和语义，不接收左侧正文数组。
- `knowledge-harness.astro`：显式建立章节与视觉组件的映射，并保留 Deck、timeline、源码方法论链接和页面入口。

### 9.3 内容模型

左侧叙事使用明确结构：

```ts
type NarrativeBlock = {
  label: string;
  body: string;
  tone: 'problem' | 'thinking' | 'decision' | 'result' | 'status';
};

type HarnessSection = {
  id: 's2' | 's3' | 's4' | 's5' | 's6' | 's7' | 's8' | 's9' | 's10';
  chapter: string;
  heading: string;
  narrative: readonly NarrativeBlock[];
  visualId: string;
};
```

`visualId` 只用于绑定唯一组件和测试，不允许作为通用图形模板的分支开关，将九种拓扑重新塞回一个巨型组件。

## 10. 交互、响应式与无障碍

保留：

- `DeckLayout`。
- 主滚动容器和逐段单屏浏览。
- timeline 锚点、当前 section 高亮和简体中文标签。
- 主题切换。
- S2 到 Claude Code 架构方法页的来源链接。
- 现有 `/ai/knowledge-harness/` URL。

移动端：

- 390px 视口不得横向溢出。
- SVG 使用稳定 `viewBox`，在容器内等比缩放。
- 结构图内部文字允许合理换行，但不得裁掉节点、图例或图注。
- 复杂图形可增加垂直高度，不用缩到无法阅读。

无障碍：

- 每张结构图有唯一 `aria-label` 或 `<title>`。
- 图注使用可读文本，不只存在于 SVG 图形内。
- 状态不能只靠颜色表达。
- timeline 链接继续可通过键盘访问。

## 11. 异常与降级

页面是静态页面，不包含运行时接口请求。需要处理的异常主要是内容和布局异常：

| 异常 | 处理 |
| --- | --- |
| 视觉组件缺失或章节映射错误 | 类型或构建失败，不允许静默显示空卡片 |
| 左右文本完全相同 | 自动化测试失败 |
| 图形文字过长 | 调整本图节点或布局，不退回通用卡片列表 |
| 移动端图形过密 | 增加图形纵向高度或重排节点，不隐藏语义节点 |
| V1/V2 状态来源冲突 | 停止更新相关页面，重新核对当前主线状态和可复核证据 |
| 截图基线变化 | 人工查看差异后再更新快照，不自动接受 |

## 12. 测试与验收

### 12.1 结构契约

- 页面有 10 个 section。
- S2–S10 有 9 个视觉组件。
- 9 个组件拥有唯一 `data-visual` 标识。
- 每个章节显式绑定一个唯一结构图。
- S1–S10 timeline 锚点与 section 一一对应。

### 12.2 左右语义去重

逐页提取：

- 左侧 `.narrative-copy` 文本。
- 右侧 `.diagram-labels` 文本。

规范化空白与标点后，两者不得完全相同。测试还需检查右侧组件没有接收左侧 `narrative` 或 `points` 数组。

该测试允许共享必要术语，例如“领域索引”“PRD Writer”，但禁止逐句复制。

### 12.3 内容与状态契约

必须出现：

- Enterprise Knowledge Harness。
- 企业知识与 Skill 解耦。
- 三层、任务与项目索引当前已使用。
- V1 稳定基线。
- V2 已实现但暂未激活。
- Query Planner、RoleRetriever、RRF / Reranker、Selector、Quality Gate 的正确职责。
- PRD Writer、独立 Reviewer 和已确认团队结果。

不得出现：

- Personal Knowledge Harness。
- 个人稳定自用、尚未推广给团队。
- 两个独立检索 / Reviewer Skill 已上线。
- V2 已正式替换 V1。
- 用技术测试数量冒充企业业务结果。

### 12.4 视觉回归

- S2–S10 九张内容页分别建立桌面端截图基线。
- S3 分层架构、S6 上下文组装、S9 版本演进增加 390px 移动端截图。
- 截图基线覆盖左右信息层级、图形拓扑、图例、图注和文字溢出。
- 更新截图必须经过人工查看，不因 E2E 其他断言通过而自动接受。

### 12.5 原有功能回归

- Astro check 和 build 通过。
- Knowledge Harness、AI 列表、Claude Code 架构桥接相关 E2E 通过。
- timeline 高亮、主题切换、源码方法论链接和旧 URL 正常。
- 桌面端和 390px 移动端无横向溢出。
- 逐页人工查看完成并记录结果。

## 13. 实施边界

本次实施只应修改或新增：

- Knowledge Harness 页面。
- Knowledge Harness 专用内容数据和视觉组件。
- Knowledge Harness 专用测试与视觉基线。
- 必要时对现有 Knowledge Harness 相关 E2E 做定向调整。

不应修改：

- 简历事实母稿与 PDF。
- About、Skill Desk、销售线索和其他项目页。
- `DeckLayout` 的全局视觉系统；只有修复该页面必须且不影响其他 Deck 的兼容调整才允许进入计划。
- memory-loader、Knowledge Context V1/V2、Obsidian Vault 或 shared Skill。

## 14. 完成标准

只有同时满足以下条件，修复才算完成：

1. 企业版十段故事完整，项目事实与完整版简历一致。
2. V1/V2 状态与当前证据一致，没有把 V2 写成已切流。
3. 左侧使用灵活语义标签，右侧是九张可独立理解的结构图。
4. 右侧不复述左侧正文，也不使用同一数组重复渲染。
5. 旧版的信息密度和案例故事感恢复，但旧个人叙事没有回流。
6. 桌面与移动端视觉基线通过人工查看。
